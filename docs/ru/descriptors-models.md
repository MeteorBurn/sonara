# Перцептивные дескрипторы, структура, сходство и встроенные модели

Глава описывает верхний слой SONARA 0.3.7: значения, которые библиотека
выводит поверх низкоуровневых признаков (RMS, спектральный центроид, мел-
спектрограмма, хрома, онсеты, биты). Низкоуровневый DSP описан в
[dsp.md](./dsp.md), ритм и тональность (BPM, битгрид, детальный алгоритм
тональности) в [rhythm-tonality.md](./rhythm-tonality.md), публичный API в
[api.md](./api.md), [оглавление](README.md), обзор на английском в [README.md](../../README.md).

Все утверждения ниже сверены с исходным кодом ревизии `0c2a4b3`. Там, где
README отстаёт от кода, это отмечено явно в конце главы.
Приведённые ниже AUC, accuracy и размеры наборов — исторические результаты
из комментариев и сохранённых evidence-файлов. При подготовке документации
эти эксперименты не повторялись; они не гарантируют точность на новой коллекции.

## 1. Три типа вычислений

В коде сосуществуют три принципиально разных класса выходов, и их важно
различать при интерпретации чисел.

| Класс | Что это | Модули | Примеры полей |
| --- | --- | --- | --- |
| Детерминированный DSP | Формулы без обучения; часть опирается на стандарты, часть — на собственный формат. Ограничения соответствия стандартам описаны ниже | `perceptual.rs` (LUFS), `loudness_ext.rs`, `fingerprint.rs` | `loudness_lufs`, `true_peak_db`, `loudness_range_lu`, `fingerprint` |
| Эвристика (взвешенная сумма нормированных скаляров) | Постоянные веса, подобранные вручную и откалиброванные на реальной музыке; не обучены | `perceptual.rs`, `mood.rs`, `structure.rs`, `similarity.rs`, `vocal.rs`, `analyze.rs` (vocalness v2) | `energy`, `danceability`, `valence`, `acousticness`, `mood_*`, `vocalness`, `energy_level`, `similarity` |
| Обученная модель | Веса получены обучением на размеченных данных, артефакт версионирован и проверяется при загрузке | `genre.rs` + `python/sonara/genre.py`, `vocal_model.rs` + `python/sonara/vocal_model.py`, `aggression.rs` + `aggression_dsp.rs` | `genre`, `vocalness` (при заданной модели), `aggression_score` |

Большинство агрегатов переиспользуют общий проход
[`analyze_signal_inner`](../../sonara/src/analyze.rs). Громкость и true peak
дополнительно обрабатывают временной сигнал. У отпечатка отдельный спектральный
проход на 11 025 Гц. Для агрессии при другой основной частоте используется
собственный узкий проход на канонических 22 050 Гц; при совпадении частот
общий конвейер переиспользует свои покадровые вычисления.

## 2. Громкость: LUFS и расширенный набор

Источники: [perceptual.rs](../../sonara/src/perceptual.rs),
[loudness_ext.rs](../../sonara/src/loudness_ext.rs).

### 2.1 Интегральная громкость `loudness_lufs`

Оценка на основе K-взвешивания BS.1770, **не полный измеритель R128**.
Анализируется моно-сигнал, без многоканального суммирования и блочного
гейтирования интегральной громкости. K-взвешивание — два каскадных биквада
(Direct Form II Transposed), коэффициенты пересчитываются под текущую частоту
дискретизации через билинейное преобразование:

- ступень 1: высокочастотная полка около +4 дБ выше 1 500 Гц (аналоговый
  прототип с `f0 = 1681.97 Гц`, `G = 3.9998 дБ`, `Q = 0.7072`);
- ступень 2: ФВЧ около 38 Гц (`f0 = 38.135 Гц`, `Q = 0.5003`).

Затем `LUFS = -0.691 + 10·log10(mean_sq)`. Тишина или пустой сигнал дают
`-70.0` (абсолютный гейт EBU R128). Интегральное значение **не гейтируется**
блоками, как это делает полный R128: это одно среднеквадратичное по всему
треку. Функция `k_weighted_signal` отдаёт тот же отфильтрованный сигнал
наружу, чтобы `loudness_ext` не дублировал фильтр.

### 2.2 Опциональный набор `features=["loudness"]`

Все функции чистые и считаются только по запросу. `loudness_metrics`
K-взвешивает сигнал один раз, строит f64-префиксную сумму квадратов и из неё
получает три величины за один проход.

| Поле | Формула | Единицы | Граничные случаи |
| --- | --- | --- | --- |
| `true_peak_db` | `20·log10(max\|x_os\|)`, где `x_os` — 4-кратная передискретизация 48-отводным полифазным sinc-фильтром с окном Блэкмана (12 отводов на фазу, каждая фаза нормирована на единичный DC-коэффициент) | dBTP | пустой вход или пик ≤ 1e-12 → `-70.0` |
| `replaygain_db` | `-18 - loudness_lufs` | дБ | чистая арифметика, без DSP |
| `loudness_curve` | R128-громкость каждого окна 3 с с шагом 1 с | LUFS на окно | трек короче окна → пустой список |
| `loudness_momentary_max_db` | максимум по окнам 400 мс с шагом 100 мс | LUFS | трек короче 400 мс — одно окно на весь сигнал |
| `loudness_range_lu` | EBU Tech 3342: абсолютный гейт -70 LUFS, относительный гейт `(энергетическое среднее) - 20 LU`, затем `p95 - p10` | LU | менее двух годных блоков → `0.0` |

Особенность true peak: спецификация BS.1770-4 задаёт таблицу коэффициентов
для 48 кГц, а SONARA работает на произвольной частоте, поэтому строит
эквивалентный интерполятор на лету. Фаза 0 воспроизводит входные отсчёты
точно, поэтому результат никогда не ниже пика по отсчётам. Тесты проверяют
синус полной шкалы (≈0 dBTP), половинной (≈-6.02 dBTP) и межотсчётный
перегруз на fs/4.

`dynamic_range_db` из основного прохода (p95 − p5 RMS в дБ) — это **грубое
приближение** к LRA, а не стандарт; `loudness_range_lu` его не заменяет и не
изменяет.

## 3. Эвристики Tier 1: энергия, танцевальность

Источник: [perceptual.rs](../../sonara/src/perceptual.rs). Модуль сам
объявляет ярусы: Tier 0 — стандарт (LUFS), Tier 1 — «привязанные к
сигналу» эвристики (энергия, танцевальность, тональность), Tier 2 — грубые
приближения (valence, acousticness, mood, instrumentalness), Tier 3 — жанр,
для которого встроенной модели нет.

### 3.1 `energy` (0..1)

Четыре скаляра нормируются линейно с зажимом в `[0, 1]` по эмпирическим
диапазонам музыки, затем взвешенная сумма проходит через сигмоиду:

```text
norm_rms      = rms_mean / 0.5
norm_centroid = (centroid_mean - 500) / 4500
norm_onset    = onset_density / 10
norm_bw       = (bandwidth_mean - 500) / 3500
w = 0.35·norm_rms + 0.25·norm_centroid + 0.25·norm_onset + 0.15·norm_bw
energy = 1 / (1 + exp(-4·(w - 0.45)))
```

Эта же функция используется покадрово в `structure.rs` для `energy_curve` и в
лейне агрессии как один из 39 признаков, поэтому изменение её констант
затрагивает три семейства выходов.

### 3.2 `danceability` (0..1)

По умолчанию используется `danceability_heuristic`, а не DFA:

- регулярность бита `beat_reg = 1 - CV(межбитовых интервалов)` (нужно ≥ 3
  бита, иначе 0);
- темповый «сладкий» пик — гауссиана с центром 120 BPM и σ = 30;
- плотность онсетов — гауссиана с центром 4 онс/с и σ = 2;
- `raw = 0.4·beat_reg + 0.35·tempo + 0.25·onset`;
- логистическая перекалибровка 0.2.4: `1 / (1 + exp(-12.3·(raw - 0.804)))`.

Перекалибровка строго монотонна (порядок сохранён), но абсолютная шкала
изменилась: на реальной музыке p5 ≈ 0.20, p50 ≈ 0.78, p95 ≈ 0.90. Пороги,
подобранные на 0.2.2/0.2.3, нужно пересчитать.

`danceability_dfa` (Streich & Herrera 2005, детрендированный флуктуационный
анализ по 10-мс кадрам, τ от 30 до 800 кадров с шагом ×1.1) реализован в том же
модуле, но слитный проход его не вызывает; это отдельная публичная функция.

### 3.3 Тональность и Camelot

`detect_key` — корреляция Пирсона хромы с 24 профилями Temperley (MIREX
2005), уверенность `= (best - second) / |best|` с зажимом. `camelot` /
`key_camelot` переводят тонику и лад в код колеса Camelot (минор — кольцо
«A», мажор — «B»), `detect_key_candidates` отдаёт топ-3 по той же корреляции с
гарантией, что первый кандидат совпадает с `detect_key`. Подробный алгоритм и
его ограничения описаны в [rhythm-tonality.md](./rhythm-tonality.md); здесь
важно лишь то, что `valence`, `mood_*` и измерение 41..46 эмбеддинга берут лад
и уверенность именно отсюда.

## 4. Эвристики Tier 2: valence, acousticness, mood, instrumentalness

### 4.1 `valence` (0 = грустно/темно, 1 = радостно/ярко)

```text
mode_score = 0.5 если key_confidence < 0.05; 0.7 для мажора; 0.3 для минора
tempo      = clamp((bpm - 60) / 120)
brightness = clamp((centroid_mean - 1000) / 3000)
valence    = 0.45·mode_score + 0.30·tempo + 0.25·brightness
```

Из-за фиксированных 0.3/0.7 диапазон значений сжат: без крайних темпа и
яркости valence не достигает 0 или 1. Это не вероятность и не откалиброванная
шкала.

### 4.2 `acousticness` (0 = электронное, 1 = акустическое)

```text
tonal  = 1 - clamp(flatness_mean · 16)
hf     = 1 - clamp((rolloff_mean - 1800) / 4000)
bright = 1 - clamp((centroid_mean - 1050) / 2300)
calm   = 1 - clamp(onset_density / 5.2)
acousticness = clamp(0.30·tonal + 0.30·hf + 0.20·bright + 0.20·calm)
```

Перекалибровано в 0.2.4: раньше тональный член упирался в ≈0.51 на реальной
музыке; добавлен член яркости. Заявленное поведение по коду: электронный
материал < 0.3, акустический > 0.6.

### 4.3 `mood_happy / mood_aggressive / mood_relaxed / mood_sad`

Источник: [mood.rs](../../sonara/src/mood.rs), реэкспорт через
`perceptual::mood_scores` для совместимости. Опциональны
(`features=["mood"]`), считаются все четыре вместе. Это **эвристика v1**, не
классификатор; четыре числа коррелированы, но не нормированы в сумме к 1.

Нормированные члены: `major/minor` (1/0, 0/1, либо 0.5/0.5 при уверенности
тональности < 0.05), `tempo = (bpm - 60)/120`, `brightness = (centroid -
1000)/3000`, `onset = onset_density/8`, `diss` — зажатая диссонансность (0,
если не посчитана), `narrow_dyn = 1 - dynamic_range_db/20`, а также `energy`
и `dance`, пересчитанные внутри из тех же скаляров.

```text
happy      = 0.35·major + 0.25·tempo      + 0.20·brightness + 0.20·dance
aggressive = 0.35·energy + 0.30·onset     + 0.20·diss       + 0.15·minor
relaxed    = 0.30·(1-energy) + 0.25·slow  + 0.25·low_onset  + 0.20·narrow_dyn
sad        = 0.35·minor + 0.25·slow       + 0.20·darkness   + 0.20·(1-energy)
```

`mood_aggressive` и `aggression_score` — разные вещи: первое — взвешенная
сумма из четырёх слагаемых, второе — обученная модель на 39 признаках
(раздел 10). По [карте проверок](../../tests/fidelity_gates.json) домен точности
`mood_aggression` заблокирован: размеченного гейта для mood нет.

### 4.4 `instrumentalness`

Всегда `clamp(1 - vocalness)` от того же значения, что и `vocalness` (раздел
8): либо эвристика v2, либо вероятность модели. Отдельного алгоритма нет.
Это описывает **отсутствие заметного вокала**, а не присутствие живых
инструментов.

## 5. Структура трека (`features=["structure"]`)

Источник: [structure.rs](../../sonara/src/structure.rs). Модуль опционален и
никогда не считается режимами `compact`/`playlist`/`full`. Все входы уже
посчитаны слитным проходом: покадровые RMS, центроид, полоса, мел-dB
спектрограмма и матрица DCT.

### 5.1 Кривая энергии

Окна `WIN_SEC = 1.0 с` с шагом `HOP_SEC = 0.5 с` (в кадрах: округление
`fps·0.5`, поэтому фактический `energy_curve_hop_sec` возвращается из
результата, а не берётся как константа). В окне усредняются RMS, центроид,
полоса, считается локальная плотность онсетов, и всё это идёт в тот же
`perceptual::energy`. Время i-й точки: `t = i · energy_curve_hop_sec`.

### 5.2 Границы секций (новизна Фута)

1. Дескриптор окна — среднее 13 MFCC (DCT от среднего мел-dB по окну).
2. Дескрипторы центрируются по измерениям и L2-нормируются; матрица
   самоподобия — косинусная.
3. Вдоль диагонали скользит «шахматное» ядро с гауссовой огибающей,
   полуширина `KERNEL_SEC = 4 с` (σ = половина ядра).
4. Кривая новизны нормируется на максимум (только положительная часть),
   порог `mean + 2.0·std`, но не ниже `0.25`; кандидаты — строгие локальные
   максимумы; жадный выбор по убыванию новизны с минимальным интервалом
   `MIN_SEGMENT_SEC = 8 с` и потолком `MAX_BOUNDARIES = 11` внутренних
   границ.

Порог `2.0·std` откалиброван на случайной выборке из 60 коммерческих треков
так, чтобы медиана была ≈8 сегментов и потолок срабатывал реже 10 % случаев;
подбор порога под **точность** границ по размеченным данным в коде прямо
назван будущей работой. Защита от вырожденных входов: если максимальное
отклонение дескрипторов меньше 1 % их масштаба (или ниже 1e-3), сегментация
не запускается и трек становится одним сегментом. Граница также отбрасывается,
если она ближе 4 с к началу или концу.

`segments` — непрерывные, упорядоченные, покрывают весь трек, у каждого есть
средняя энергия по окнам, чьё начало попало в отрезок.

### 5.3 Интро / аутро

Это откровенно эвристика: `thresh = p10 + 0.5·(p90 - p10)` по кривой энергии;
`intro_end_sec` — начало первого окна, достигшего порога; `outro_start_sec` —
конец последнего такого окна. Оба притягиваются к ближайшей внутренней
границе, если она ближе `SNAP_SEC = 5 с`. Если после этого интро не раньше
аутро, возвращается `(0, duration)`. Плоский трек: `intro_end = 0`,
`outro_start = duration`.

### 5.4 `energy_level` (1..10)

```text
t = clamp((mean_energy - 0.25) / (0.60 - 0.25))
energy_level = 1 + round(9·t)
```

Сигмоида `energy` на реальной библиотеке (9 400 треков поп/хип-хоп/танцевальной
музыки по комментарию в коде) даёт среднее по треку от ≈0.25 до ≈0.62 с
медианой 0.45, поэтому именно полоса 0.25..0.60 растянута на 1..10.
Отображение монотонно; тишина даёт уровень 1.

## 6. Эмбеддинг сходства и метрика

Источник: [similarity.rs](../../sonara/src/similarity.rs). Это классический,
не обученный слой: 48 измерений с **постоянной** нормировкой (никогда не
адаптивной по треку или партии), каждое в `[0, 1]`, всегда конечное.

### 6.1 Раскладка вектора (`SIMILARITY_VERSION = 2`, `EMBEDDING_DIM = 48`)

| Индексы | Блок | Нормировка |
| --- | --- | --- |
| 0 | MFCC c0 | `tanh01(x, center=-180, scale=120)` |
| 1..13 | MFCC c1..c12 | `tanh01(x, 0, 30)` |
| 13..25 | хрома (12 классов) | зажим `[0, 1]` (уже относительная) |
| 25..31 | спектральный контраст, 6 полос | `lin01(x, 0, 5)` |
| 31..35 | центроид, полоса, роллофф, плоскостность | `lin01` по 500..5000 Гц, 500..4000 Гц, 0..8000 Гц, 0..0.25 |
| 35..39 | ритм: `fold_bpm`, плотность онсетов (0..12), `danceability`, регулярность сетки | см. ниже |
| 39..41 | динамика: LUFS (−40..0), `dynamic_range_db` (0..30) | `lin01` |
| 41..46 | тональное: диссонанс, частота смен аккордов (0..4/с), sin/cos на квинтовом круге, лад (мажор 1 / минор 0) | — |
| 46..48 | `energy`, `valence` | зажим; 0.5, если отсутствуют |

`tanh01(x, c, s) = 0.5 + 0.5·tanh((x - c)/s)`; `fold_bpm` сворачивает темп в
диапазон `[60, 180)` октавными удвоениями/делениями и берёт
`log2(b/60)/log2(3)`; сам диапазон шире одной октавы. Регулярность сетки —
`1 - CV(межбитовых интервалов)`. Отсутствующие поля заменяются
задокументированными нейтральными значениями, поэтому вектор всегда полной
длины, но для осмысленного сходства нужно запрашивать `features=["embedding"]`.

Версия 2 введена 2026-07-17 из-за смены хрома-фильтрбанка (октавное
взвешивание в стиле librosa): векторы, построенные раньше, несравнимы с v2.
Правило: любое изменение раскладки, констант нормировки или таблицы весов
профиля по умолчанию требует инкремента `SIMILARITY_VERSION`, а это
инвалидирует жанровые и вокальные модели, а также legacy-скорер агрессии,
потребляющие embedding. Fused-aggression имеет отдельную 39-мерную схему
входов и собственные версии, а не принимает этот 48-мерный вектор.

### 6.2 Дистанция, сходство, профили

Метрика — взвешенная нормированная евклидова, не косинусная (все измерения
неотрицательны и ограничены, косинус был бы смещён к 1):

```text
distance   = sqrt( Σ w_i·(a_i - b_i)² / Σ w_i )        ∈ [0, 1]
similarity = clamp(1 - distance / SIMILARITY_SCALE)     SIMILARITY_SCALE = 0.38
```

Растяжение откалибровано на библиотеке 9 400 треков: случайные пары дают
сырое расстояние ≈0.08..0.27 (медиана ≈0.19), соседи одного артиста ≈0.13;
масштаб выбран как 2× медианы, чтобы случайная пара давала ≈0.5, соседи
0.65+, идентичный трек ровно 1.0. Преобразование монотонно, ранжирование по
`distance` и `similarity` совпадает.

Два профиля весов применяются **во время сравнения**, хранимый вектор
неизменен:

- `default` (`WEIGHTS`, версия = `SIMILARITY_VERSION`): темп 2.0 — самый
  тяжёлый вес, MFCC 0.4..1.0, хрома 0.7, контраст 0.7, LUFS 0.3.
- `timbre` (`WEIGHTS_TIMBRE`, `SIMILARITY_PROFILE_TIMBRE_VERSION = 1`): MFCC
  c1..c5 по 2.0, контраст 1.6, темп 0.3, энергия 0.3, valence 0.2. По
  комментарию в коде тембровые блоки несут ≈77 % массы против ≈48 % в
  профиле по умолчанию. Для тембрового профиля переиспользован тот же
  `SIMILARITY_SCALE`; отдельная калибровка отложена.

Если хотя бы один вектор не длины 48, веса не применяются и берётся
равномерная метрика по общему префиксу. Неизвестное имя профиля должно быть
отвергнуто вызывающим кодом (Python-обёртка бросает `ValueError`).

Замороженный аудио-независимый гейт: `tests/reference_data/similarity_frozen_v1.json`
(91 попарное расстояние и 14 ранжирований по CHANGELOG 0.3.5).

## 7. Отпечаток для поиска дубликатов (`features=["fingerprint"]`)

Источник: [fingerprint.rs](../../sonara/src/fingerprint.rs). Это
детерминированный DSP без обучения; `FINGERPRINT_VERSION = 1`.

Отличие от эмбеддинга принципиально: **эмбеддинг** отвечает «насколько похоже
звучат две разные записи», **отпечаток** — «одна ли это и та же запись в
разных кодировках». Отпечаток не переживает изменение темпа или высоты и не
годится для «похожести».

Алгоритм:

1. Ресемплинг до `FP_SR = 11 025 Гц` (всё выше ≈5.5 кГц, где кодеки расходятся
   сильнее всего, отбрасывается).
2. Кадры `N_FFT = 2048` с шагом `HOP = 1378` (≈8 кадров/с), окно Ханна,
   мощностной спектр.
3. `N_BANDS = 33` логарифмически распределённых полосы в 300..2000 Гц,
   `L = ln(E + 1e-10)`.
4. Один бит на пару соседних полос и соседних кадров:
   `D(t,m) = (L(t,m) - L(t,m+1)) - (L(t-1,m) - L(t-1,m+1))`, бит = `D > 0`.
   33 полосы → 32 бита → ровно один `u32` на кадр.

В идеальном log-домене глобальное усиление добавляет константу ко всем `L`
и сокращается разностями. Это объясняет устойчивость к уровню, но добавка
`1e-10`, квантование и переходы знака около нуля не дают абсолютной численной
инвариантности. Постоянная окраска полос также ослабляется разностью по времени.

Сопоставление `match_score`: сдвиг ±24 кадра (≈3 с), минимальное перекрытие
`max(4, min(len)/2)`, в лучшем выравнивании считается доля различающихся бит
BER, `score = max(0, 1 - 2·BER)`. По документации модуля порог «одна запись»
— score выше ≈0.30 (BER ниже ≈0.35); реальные дубликаты обычно > 0.7,
посторонние < 0.15. Сериализация — little-endian `u32` в стандартном base64
без зависимостей; `decode_base64` возвращает `None` при некорректной длине.

## 8. Вокальность: три реализации, одна по умолчанию

Это место, где README отстаёт сильнее всего, поэтому по коду:

| Реализация | Где | Статус | Что измеряет |
| --- | --- | --- | --- |
| v1, мел-эвристика | [vocal.rs](../../sonara/src/vocal.rs), функция `vocalness(mel_spec, sr, hop)` | **устарела**, в результат анализа не попадает | тональность + силлабическая модуляция 4–8 Гц в полосе 200–4000 Гц |
| v2, контрастная эвристика | `vocalness_heuristic_v2` в [analyze.rs](../../sonara/src/analyze.rs) | **значение по умолчанию** для `features=["vocalness"]` без модели | заполненность спектральных «долин» 0.8–5.6 кГц |
| Обученная модель `sonara-vocalness-v2` | [vocal_model.rs](../../sonara/src/vocal_model.rs), артефакт [models/vocalness_v2.json](../../sonara/models/vocalness_v2.json) | включается явно: `vocalness_model="bundled"` или путь к своему JSON | P(vocal) по 48-мерному эмбеддингу |

### 8.1 Почему v1 отброшена

v1 гейтирует тональность и модуляцию: `core = sqrt(tonal · mod_eff)`,
`vocalness = 0.75·core + 0.15·er + 0.10·cv`. На размеченном наборе её
AUC(vocal > instrumental) составила 0.289, хуже случайного: кричащий вокал
широкополосен и проваливает тональный гейт, а чистый саксофон или скрипка
проходят оба. Функция сохранена только из-за публичной сигнатуры и её тесты
проверяют то, что она реально считает.

### 8.2 Эвристика v2 (по умолчанию)

```text
c_mid      = (contrast[2] + contrast[3] + contrast[4]) / 3      // ~0.8–5.6 кГц
v_contrast = clamp((2.05 - c_mid) / (2.05 - 1.35))
lift       = 0.15 · clamp((flatness_mean - 0.02) / 0.05)        // только вверх
vocalness  = min(v_contrast + lift, 1)
```

Тишина (`rms_mean < 1e-5`) даёт `0.0`, а не ложное «максимально вокально».
Требует расширенного прохода (контраст и плоскостность), поэтому в реестре
признаков `vocalness` и `instrumentalness` помечены как extended. По
комментариям в коде порядок «резкий > чистый > инструментал» получен с AUC
≈0.92 на исследовательском наборе, но модуль `vocal_model.rs` приводит для
той же эвристики AUC ≈0.63 на другом размеченном наборе с большим кластером
ложноотрицательных чистых вокалов. Две цифры относятся к разным наборам;
кода, который бы их воспроизводил в репозитории, нет, поэтому опираться стоит
на второй, более пессимистичный вывод: эвристика не отделяет чистый сольный
голос от чистого сольного инструмента.

### 8.3 Модель `sonara-vocalness-v2`

Формат — JSON-формат жанровой модели (`format_version = 1`) с тремя
дополнительными требованиями, проверяемыми при загрузке: непустой `id`,
ровно две метки, одна из которых `"vocal"` (без учёта регистра). Выход —
softmax-вероятность метки `vocal`, а не argmax.

Встроенный артефакт по данным файла: `id = "sonara-vocalness-v2"`,
`embedding_version = 2`, метки `["instrumental", "vocal"]`, два слоя
`48 → 32 (relu) → 2 (softmax)`. Он встроен в крейт через `include_str!` и
продублирован байт-в-байт в `python/sonara/models/`; тест
`test_bundled_matches_python_package_artifact` падает при расхождении копий.

Валидация зафиксирована в
[tests/reference_data/vocalness_v2_validation.json](../../tests/reference_data/vocalness_v2_validation.json):

| Набор | Примеров | v1 AUC | v2 AUC | v2 FN / FP |
| --- | ---: | ---: | ---: | ---: |
| fresh (непересекающийся) | 199 (92 вок. / 107 инстр.) | 0.943 | 0.947 | 7 / 18 |
| cached | 90 (53 / 37) | 0.697 | 0.865 | 6 / 10 |
| broad_fresh_v2 | 205 (96 / 109) | — | 0.948 | 6 / 19 |

Здесь v1/v2 — поколения **обученной модели**, а не mel- и контрастная
эвристики из предыдущих подразделов.

Обучение: 906 fresh + 173 cached примеров, 11 исключений по хешам замороженной
фикстуры, `hidden = 32`, 3 500 эпох, seed 15, L2 = 1e-3. Хеш артефакта
`0d629a04…6847` и хеш фикстуры закреплены в том же файле. Известные
ограничения по docstring `bundled_path`: сольные мелодические инструменты
(сакс, гитара) могут читаться как вокал, речевое повествование получает
низкий балл.

Вход модели — тот же 48-мерный эмбеддинг, поэтому при заданной модели анализ
автоматически строит эмбеддинг, даже если `embedding` не запрошен (поле в
результат при этом не эмитируется). `embedding_version` модели сверяется с
`SIMILARITY_VERSION` **до** тяжёлого DSP; несовпадение — ошибка, а не
молчаливая деградация. `provenance.vocalness_model_id` содержит `id` модели
или `None` для эвристики; кэши обязаны трактовать смену этого поля как
инвалидацию хранимых `vocalness`/`instrumentalness`.

### 8.4 Тренер `python/sonara/vocal_model.py`

Чистый numpy, без sklearn/torch. `train(X, y, model_id=..., hidden=16,
epochs=2000, lr=0.05, seed=0, l2=1e-3)`: признаки стандартизируются по
обучающей выборке, классы взвешиваются обратно частоте, инициализация He
(`sqrt(2/d)`), полный градиентный спуск. Стандартизация **сворачивается в
первый слой** (`W1/σ`, `b1 - (μ/σ)·W1`), так что сохранённая модель работает
на сырых эмбеддингах. Согласованность Rust и NumPy проверяется с численным
допуском; битовое совпадение не гарантируется. `hidden=0`
— логистическая регрессия. `LABELS` фиксированы как
`["instrumental", "vocal"]`, индекс 1 — P(vocal). `model_id` обязателен.

## 9. Жанр: пустой сокет

Источники: [genre.rs](../../sonara/src/genre.rs),
[python/sonara/genre.py](../../python/sonara/genre.py). SONARA **не поставляет**
жанровую модель; поле `genre` заполняется только при `genre_model=<путь>`.

Формат JSON (`GENRE_MODEL_FORMAT_VERSION = 1`) содержит `format_version`,
`embedding_version`, необязательный `id`, список строк `labels` и список
объектов `layers`. Каждый слой содержит числовую матрицу `weights`, вектор
`bias` и строку `activation`. Реальный файл создаёт `model.save(path)` после
обучения; это не файл с названиями архитектуры вместо весов.

Слой: `out = activation(W·x + b)`, `W` row-major (`out_dim` строк по `in_dim`).
Активации: `relu`, `softmax`, `identity`. Валидация при загрузке: первый
`in_dim = 48`, размерности слоёв сцеплены, последний слой — softmax с
`out_dim = labels.len()`, строки не рваные, все числа конечны;
`format_version` должен совпадать точно. Парсер JSON — собственный
рекурсивный спуск без serde, отвергает любой мусор после корневого значения.
`id` необязателен (аддитивен в формате v1) и при наличии уходит в
`provenance.genre_model_id`.

Инференс: `predict` — argmax softmax, при точном равенстве вероятностей
выбирается меньший индекс (паритет с `numpy.argmax`, зафиксировано в 0.3.2).
Небезопасные входы (NaN, неверная длина) зануляются/усекаются, а
`try_predict` возвращает ошибку при нефинитных параметрах или ненормированном
выходе; нефаллибельный `predict` в этом случае отдаёт `("unknown", 0.0)`.
`embedding_version` проверяется при **использовании**, не при загрузке, чтобы
устаревший файл можно было инспектировать.

Тренер `genre.train(X, y, hidden=0, epochs=300, lr=0.1, seed=0, l2=0.0)` —
softmax-регрессия или один скрытый ReLU-слой; в отличие от вокального тренера
признаки **не** стандартизируются и классы не взвешиваются. Метки —
отсортированные уникальные строки из `y`. Домен точности `genre` в
[fidelity_gates.json](../../tests/fidelity_gates.json) заблокирован:
размеченного гейта нет, что логично для сокета без модели.

## 10. Агрессия: обученная модель на 39 признаках

Источники: [aggression.rs](../../sonara/src/aggression.rs),
[aggression_dsp.rs](../../sonara/src/aggression_dsp.rs), артефакты
`sonara/src/aggression_model.bin` (7 080 байт) и
`sonara/src/aggression_linear.ferricml` (264 байта), встроенные через
`include_bytes!`. Требует cargo-фичи `aggression` (подтягивает `ferricml` и
`sha2`); Python-биндинг всегда собирается с ней, а `cargo test -p sonara` без
фичи этот код не компилирует.

### 10.1 Две модели, два идентификатора

| Модель | ID | Вход | Тип | Где используется |
| --- | --- | --- | --- | --- |
| Legacy v1 | `aggression-logistic-v1` | 48-мерный эмбеддинг v2 | логистическая регрессия FerricML (артефакт 300 байт, зашит в код) | `aggression::score`, `score_versioned`, Python `aggression_score(embedding, embedding_version=)` — для переоценки **хранимых** эмбеддингов |
| Текущая v3 | `aggression-rank-v3-sr22050` | 39 слитных признаков | линейный ранг FerricML + ансамбль из 16 деревьев | `features=["aggression"]`, `analyze_aggression_*`, `aggression::analyze_file/signal/batch` |

Legacy-путь проверяет, что `embedding_version == 2 == SIMILARITY_VERSION`,
длину 48 и конечность значений; иначе ошибка. Слитный анализ его **не**
использует начиная с 0.3.1 (схема результата v5; каноническая частота 22 050 Гц
добавлена в 0.3.3, схема v6): `aggression_score` в результате — всегда v3.

### 10.2 Узкий проход на 22 050 Гц

Вход любой частоты ресемплируется до `AGGRESSION_SAMPLE_RATE = 22 050 Гц`
(схема v6): модель обучалась в этой области, и её выход не должен зависеть от
частоты, которую попросил вызывающий. Основные поля результата при этом
остаются в частотной области вызова. `aggression_dsp` повторяет арифметику
общего анализатора (STFT 2048/512, 128 мел, Ханн, слэни-фильтрбанк, DCT только
для MFCC 0 и 2, 5 из 6 контрастных полос, диссонанс Пломпа–Левельта по ≤50
пикам 40–5000 Гц), но пропускает всё, что не нужно модели. Покадрово
дополнительно считаются:

- crest-фактор `20·log10(peak/rms)` по кадру;
- доля энергии выше 4 кГц (`high_energy_ratio`), плоскостность этой области
  (`high_flatness`), её суммарная мощность (для `high_flux`);
- `peak_ratio` — доля мощности в 8 сильнейших бинах (спектральная
  «пиковость»).

Трекинг битов и онсетов запускается на собственном онсет-огибающем
(средний положительный мел-dB-флюкс) с теми же параметрами, что и в основном
проходе.

### 10.3 Семейства признаков (39 значений)

Все значения нормируются в `[0, 1]` теми же приёмами, что и эмбеддинг
(`unit(x, hi) = clamp(x/hi)`, `lin01`, `tanh01`, `fold_bpm`).

| Группа | Признаки (индексы) | Нормировка |
| --- | --- | --- |
| Crest и диссонанс | crest p50, p90 (0,1); диссонанс p50 (2), tension = диссонанс p90 (3) | `/20 дБ`; `/0.15` |
| Тембр | MFCC c0 (4), c2 (5); контраст полос 0..4 (6..10) | `tanh01(-180,120)`, `tanh01(0,30)`; `/5` |
| Спектральные скаляры | центроид (11), полоса (12) | 500..5000 Гц, 500..4000 Гц |
| Ритм эмбеддинга | `fold_bpm` (13), плотность онсетов (14, `/12`), danceability (15), регулярность сетки (16) | как в эмбеддинге |
| Динамика/энергия | `dynamic_range_db/30` (17), `perceptual::energy` (18) | — |
| Высокочастотная резкость | high energy p50, p90 (19, 20, `/0.35`); high flatness p50 (21); `ln(1 + high_flux_p90)/ln 11` (22) | — |
| Композитные компоненты | force (23), force·harshness (24), force·tension (25), harshness (26), dance·regularity·(1−harshness) (27), tension (28) | см. ниже |
| Агрессионные онсеты | плотность (29, `/15`), CV интервалов (30, `/2`), сила p50 (31, `/2`), p90 (32, `/4`) | по порогу `max(p50 + 0.25, 0.30)` на огибающей, нормированной на её p90 |
| RMS и пики | `ln(rms_p90/rms_p10)/ln 10` (33), `peak_ratio` p50 (34) | — |
| Оконные сводки | force top-2 (35), harshness top-2 (36), устойчивость удара (37), impact top-2 (38) | окна 20 с с шагом 10 с; «top-2» — среднее двух лучших окон; устойчивость — доля окон с `force·harshness ≥ 0.25` |

Композитные компоненты, которые также отдаются наружу как диагностика:

```text
force     = ((1 - crest_p50/20) + onset_density/15 + onset_strength_p50/2) / 3
harshness = (high_energy_p50/0.35 + high_flatness_p50 + (1 - peak_ratio)) / 3
tension   = dissonance_p90 / 0.15
rhythm    = (onset_density_embedding/12 + danceability + grid_regularity) / 3
```

Признак с индексом 26 (harshness) дополнительно используется как явная
поправка в финальном смешивании.

### 10.4 Инференс и поддержка

```text
raw    = intercept + Σ w_i·(f_i - center_i)
linear = sigmoid(slope·raw + intercept_cal)
trees  = baseline + Σ leaf_value(tree_k(f))          // 16 деревьев, ≤31 узел каждое
score  = clamp(w_lin·linear + w_tree·clamp(trees) + k_h·(f[26] - 0.5))
```

Коэффициенты линейной части — из `aggression_linear.ferricml`, всё остальное
(центры, калибровка, веса смеси, `k_h`, деревья) — из `aggression_model.bin`.
Декодер проверяет SHA-256 хвоста файла, магию `SNRAGGR2`, версию артефакта 2,
число признаков 39, версию модели 3, хеш схемы признаков (тот же хеш обязан
совпасть и в FerricML-конверте), `w_lin + w_tree = 1`, положительный наклон
калибровки, `k_h ∈ [0, 0.25]`, а также структурную корректность деревьев
(лист помечен `feature = 255`, ветви ссылаются только вперёд). Любое
расхождение — `ModelError`, а не тихая деградация. Модель декодируется один
раз (`OnceLock`), инференс без аллокаций.

`aggression_confidence` — **не уверенность ранга**, а независимая мера
«достаточно ли музыкального содержимого»:

```text
content_support = non_silent · (0.5·peak_ratio_p50 + 0.5·(1 - high_flatness_p50))
```

где `non_silent` — доля кадров с RMS не ниже 10 % от p90. При
`content_support < 0.10` модель **воздерживается**: `aggression_score = None`,
компоненты и confidence при этом всё равно возвращаются. Тишина даёт 0.

Полоса ничьих `0.07` хранится в артефакте только для проверки формата; политика
ничьих в попарных сравнениях намеренно вне контракта инференса.

### 10.5 Зафиксированная валидация

[tests/reference_data/aggression_v2_evidence.json](../../tests/reference_data/aggression_v2_evidence.json)
закрепляет хеши обоих артефактов и результаты на наборе разработки: 52/64
верных решающих пар, 20/24 трудных, Spearman 0.871, MAE 0.097, минимальный
Spearman по групповым фолдам 0.760; перемешанные метки дают направленную
точность 0.528 и Spearman 0.061 (контроль утечки). Физический контроль:
резкий минус громкий-чистый синтетический сигнал = 0.436, тишина
воздерживается, оффлайн-Rust расхождение ≤ 7.8e-5. Устойчивость к частоте:
на 117 реальных файлах при 22 050/32 000/44 100/48 000 Гц через файловый API
максимальная дельта 0.0 и Spearman 1.0; через signal-API с внешним
ресемплингом туда-обратно — до 0.061 дельты, что в файле явно отнесено к
потерям внешнего ресемплинга. Замороженные goldens в юнит-тестах
(`scores_match_frozen_model_goldens`, `fused_rank_model_matches_fixed_feature_goldens`)
закрепляют битовые значения выхода для нулевого, единичного и линейного
входов. Производительность из `aggression_v2_performance.json` измерена на
Apple M4 и не переносится на другое железо.

Домен `aggression_semantic` в гейтах точности имеет `transition_policy:
"forbid"`: смена семантики модели без нового ID и версии запрещена.

## 11. Версионирование и происхождение результата

| Константа / поле | Значение в 0.3.7 | Что инвалидирует |
| --- | --- | --- |
| `ANALYSIS_SCHEMA_VERSION` | 6 | любое изменение смысла существующего поля; v3 — vocalness v2 и перекалибровка acousticness/danceability, v5 — агрессия v3, v6 — каноническая частота агрессии |
| `SIMILARITY_VERSION` | 2 | эмбеддинги, все жанровые/вокальные модели, legacy-агрессия |
| `SIMILARITY_PROFILE_TIMBRE_VERSION` | 1 | только результаты сравнений в профиле `timbre`, не векторы |
| `FINGERPRINT_VERSION` | 1 | хранимые отпечатки |
| `GENRE_MODEL_FORMAT_VERSION` | 1 | JSON-файлы моделей (жанр и вокал) |
| `AGGRESSION_MODEL_VERSION` / `AGGRESSION_MODEL_ID` | 3 / `aggression-rank-v3-sr22050` | хранимые `aggression_*` |
| `provenance.vocalness_model_id` | `sonara-vocalness-v2` или свой `id`, `None` для эвристики | `vocalness`, `instrumentalness` |
| `provenance.genre_model_id` | `id` модели или `None` | `genre`, `genre_confidence` |
| `provenance.aggression_model_id` | `aggression-rank-v3-sr22050` при запросе агрессии | `aggression_*` |

`augment_analysis` использует эти поля как ворота: несовпадение
`embedding_version` записи с текущей сборкой отклоняет любой пересчёт,
потребляющий эмбеддинг, а заданная вокальная модель переводит пару
`vocalness`/`instrumentalness` на эмбеддинг-путь (см. [api.md](./api.md)).

## 12. Ограничения, о которых стоит помнить

- Все Tier 1/2 эвристики — фиксированные веса с константами «по эмпирическим
  диапазонам музыки». Они не являются вероятностями, не откалиброваны по
  разметке (кроме перекалибровок 0.2.4 по распределениям) и должны
  использоваться как грубые теги.
- `valence` и `mood_*` опираются на лад из `detect_key`, у которого при
  уверенности < 0.05 включается нейтральное 0.5; для атонального и модального
  материала это систематически размывает оценки.
- `vocalness` по умолчанию — эвристика v2 с известным провалом на чистом
  сольном вокале; модель `sonara-vocalness-v2` включается явно. На сохранённом
  cached-наборе её AUC выше предыдущей обученной модели (0.70 → 0.86),
  но сольные мелодические инструменты всё ещё могут путаться с голосом.
- `instrumentalness` — не «присутствие живых инструментов», а `1 - vocalness`.
- Структурная сегментация откалибрована на «правдоподобное число сегментов», а
  не на точность границ; интро/аутро — пороговая эвристика по энергии.
- Эмбеддинг — ручной вектор; сходство в `[0, 1]` — линейная растяжка расстояния
  под одну коммерческую библиотеку.
- Отпечаток не устойчив к изменению темпа/высоты; порог 0.30 — из документации
  модуля, не из формального гейта (домен `fingerprint` заблокирован).
- Агрессия — ранг, а не вероятность; на слабом контенте она воздерживается,
  и `None` здесь является штатным результатом, а не ошибкой.

## 13. Расхождения README с кодом

Проверено по [README.md](../../README.md) на той же ревизии:

1. Раздел «Vocal presence» описывает только эвристику v2 и советует «обучить
   свою модель через тот же сокет», не упоминая, что встроенная модель
   `sonara-vocalness-v2` уже есть и включается `vocalness_model="bundled"`.
   Значение **по умолчанию** при этом README описывает верно: без параметра
   работает эвристика.
2. Строка описания `vocal.rs` в схеме модулей README называет его «legacy v1
   heuristic», это верно; но README нигде не приводит цифру AUC 0.289, из-за
   которой v1 отброшена, и ссылается на «socket» без указания на
   `vocal_model.rs`.
3. README перечисляет `genre` как «reserved top-level placeholder (a future
   computed field)» в разделе про теги, тогда как поле уже заполняется при
   `genre_model=`. Это остаток формулировки 0.2.x.
4. README говорит, что perceptual-набор включает `aggression_score` в списке
   «Perceptual», но не уточняет, что это legacy-скорер v1 по эмбеддингу; в
   разделе «Aggression model» разница описана корректно.
5. Про структуру README и код согласны (окно 1 с/0.5 с, новизна Фута,
   минимум 8 с, порог по p10/p90). Про отпечаток, эмбеддинг, профили и
   loudness-набор расхождений не найдено.
