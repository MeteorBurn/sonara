# Ритм и тональность

Глава описывает ритмический и тональный слой SONARA 0.3.7: как из сигнала
получается огибающая онсетов, как из неё оценивается темп и трекаются биты,
что такое сетка битов и «ритмическая регулярность», и как из спектра
получаются HPCP, аккорды, диссонанс и тональность. Всё изложено по исходному
коду; там, где документация в коде расходится с реализацией, это отмечено.

Исходники, о которых идёт речь:

| Модуль | Что делает |
| --- | --- |
| [`onset.rs`](../../sonara/src/onset.rs) | огибающая онсетов (спектральный поток), многополосные огибающие, пикинг онсетов |
| [`beat.rs`](../../sonara/src/beat.rs) | оценка темпа по ACF, DP-трекер битов, `plp`, кривая темпа |
| [`feature/rhythm.rs`](../../sonara/src/feature/rhythm.rs) | темпограммы, метрограмма, размер такта |
| [`beatgrid.rs`](../../sonara/src/beatgrid.rs) | смещение сетки, сильные доли, стабильность сетки |
| [`rhythmic_regularity.rs`](../../sonara/src/rhythmic_regularity.rs) | регулярность рисунка внутри сетки |
| [`tonal.rs`](../../sonara/src/tonal.rs) | HPCP, аккорды, диссонанс |
| [`perceptual.rs`](../../sonara/src/perceptual.rs) | тональность (ключ), кандидаты ключа, Camelot |

Соседние главы: обзор конвейера и API в [README.md](README.md) и [api.md](api.md),
низкоуровневый DSP (STFT, мел-фильтры, окна, автокорреляция) в [dsp.md](dsp.md),
эвристические и модельные дескрипторы в [descriptors-models.md](descriptors-models.md).
Пользовательская документация с примерами: корневой [README.md](../../README.md).

## Два пути: standalone и fused

У большинства функций два способа вызова.

- **Standalone.** Публичные функции модулей (`onset_strength`, `beat_track`,
  `hpcp`, …) и имеющиеся Python-обёртки. Функции с аудио-входом могут считать
  свой STFT; HPCP получает готовый спектр, а ритмические функции могут
  принимать готовую огибающую. Типичные Python-defaults: `sr=22050`, `hop_length=512`.
- **Fused.** Оркестратор `analyze_signal_inner` в [`analyze.rs`](../../sonara/src/analyze.rs)
  делает один проход по кадрам (`n_fft = 2048`, `HOP_LENGTH = 512`) и из него же
  получает мел-спектр, хрому, HPCP, диссонанс и огибающую онсетов. Ритмические
  и тональные модули там вызываются уже на готовых кривых и не запускают второй
  STFT. Например, `rhythmic_regularity` добавляет работу с татумами, окнами,
  профилями и их DFT, но не второе декодирование или STFT.

Индексы кадров у обоих путей одинаковые: время кадра `k` равно
`k * hop_length / sr` секунд. При `22050 / 512` один кадр ≈ 23,2 мс, частота
кадров ≈ 43,07 кадра/с.

## Огибающая онсетов: спектральный поток

`onset_strength` (обёртка над `onset_strength_multi` с `lag = 1`,
`max_size = None`) считает классический спектральный поток на лог-мел-спектре:

1. мел-спектрограмма: `n_fft = 2048`, 128 мел-полос, диапазон `0..sr/2`,
   степень 2 (мощность);
2. перевод в дБ через `power_to_db` с потолком динамики 80 дБ;
3. для каждого кадра `t` и полосы `m` берётся положительная разность
   `max(S_dB[m, t+lag] − R[m, t], 0)`, где `R` — «опорный» спектр;
4. сумма по полосам делится на число полос (среднее положительного потока);
5. слева добавляется `pad_left = lag + n_fft / (2 * hop_length)` нулевых кадров,
   чтобы огибающая была выровнена с центрированным STFT (при 2048/512 это
   `1 + 2 = 3` кадра).

`max_size > 1` включает опорный спектр как локальный максимум по частоте
(окно `max_size` мел-полос вокруг `m`), иначе `R = S_dB`. В fused-конвейере
огибающая считается тем же способом инлайн (`analyze.rs`, блок после
`power_to_db`), из той же лог-мел-матрицы, что идёт в MFCC.

Единицы: усреднённая положительная разность в дБ между кадрами. Значение не
нормировано и отражает изменения энергии. Постоянное усиление сигнала в
идеальном log-домене сокращается в разности; численные пороги вблизи тишины
нарушают строгую инвариантность.

### Альтернативные методы (`onset_strength_method`)

Только standalone. Все три считают собственный STFT (`n_fft = 2048`, окно Hann,
центрирование с константным паддингом) и усредняют по бинам:

- `energy` — положительная разность мощности `|S[t]|² − |S[t−1]|²`;
- `phase` — отклонение фазы второго порядка `φ[t] − 2φ[t−1] + φ[t−2]`,
  свёрнутое в `[−π, π]` и взвешенное `|S[t]|`;
- `complex` — модуль разности между реальным спектром и предсказанным
  `|S[t−1]| · exp(j(2φ[t−1] − φ[t−2]))`.

Имена в Python: `"spectral_flux"` (синонимы `"flux"`, `"spectralflux"`),
`"energy"` (`"rms"`), `"phase"`, `"complex"`. Неизвестное имя даёт `ValueError`.
Фазовые методы чувствительны к тональным атакам, но для трекинга битов
конвейер всегда использует спектральный поток.

### Многополосные огибающие (`onset_strength_bands`)

Та же лог-мел-матрица делится на смежные частотные полосы, и для каждой полосы
считается свой средний положительный поток (`lag = 1`, без опорного максимума).
Полосы **не** нормируются друг относительно друга: строка — сырой средний
поток своих мел-фильтров.

Границы по умолчанию (`default_onset_band_edges`): `0, 200, 800, 3200, 8000,
Nyquist` Гц. При низкой частоте дискретизации отбрасываются точки разбиения,
лежащие на Найквисте и выше, а также те, при которых соседняя полоса осталась
бы без единого центра мел-фильтра. Возвращаемый `band_edges_hz` всегда точно
описывает строки результата: строка `i` покрывает `[edges[i], edges[i+1])`,
последняя граница включительно.

Пользовательские границы проверяются жёстко: минимум два конечных строго
возрастающих значения в `0..=sr/2`, и каждая полоса должна содержать хотя бы
один центр мел-фильтра. Иначе — `InvalidParameter("band_edges_hz")`. Нулевые
`sr` или `hop_length` тоже ошибка.

В fused-конвейере это фича `onset_bands` (только opt-in). Она берёт уже
посчитанную лог-мел-матрицу через `onset_strength_bands_from_log_mel`, поэтому
второго STFT нет. В результате `analyze_*` огибающие лежат как список списков,
в standalone-функции — как `float32`-массив `(n_bands, n_frames)`.

### Пикинг онсетов (`onset_detect`)

Огибающая нормируется на максимум (если максимум нулевой — онсетов нет), затем
`peak_pick` с окнами, заданными в секундах и переведёнными в кадры:

| Параметр | Значение |
| --- | --- |
| `pre_max` | 0,03 с (минимум 1 кадр) |
| `post_max` | 1 кадр |
| `pre_avg` | 0,10 с |
| `post_avg` | 0,10 с + 1 кадр |
| `wait` | аргумент, или 0,03 с при `wait = 0` |
| `delta` | порог над локальным средним; конвейер использует 0,07 |

`backtrack = true` сдвигает каждый пик назад к ближайшему предшествующему
минимуму огибающей (не раньше предыдущего сдвинутого онсета). Конвейер вызывает
`onset_detect` без backtrack, и из числа найденных пиков получается
`onset_density` = онсеты / длительность в секундах. Это плотность событий,
не число нот.

## Темп и биты (`beat.rs`)

Алгоритм — динамическое программирование Эллиса (2007) поверх огибающей
онсетов. Точка входа конвейера — `beat_track_detailed`, которая возвращает
структуру `TempoEstimate` и список кадров битов; `beat_track` и
`beat_track_with_bpm_range` — тонкие обёртки.

Параметры конвейера: `start_bpm = 120`, `tightness = 100`, `trim = true`,
плюс `bpm_min`/`bpm_max` из `AnalysisConfig`.

### Защитные ветки

- Если в огибающей меньше 4 кадров — темп `start_bpm`, битов нет, кандидатов
  нет.
- Если огибающая плоская (максимум ≤ 1e−10 или размах ≤ 1e−10) — тот же
  «fallback»: тишина и DC не дают осмысленного пика ACF, и трекер не
  запускается.

### Оценка темпа по автокорреляции

1. Автокорреляция огибающей до лага `min(4 с, len)` (в кадрах).
2. Кандидаты — все целые лаги, соответствующие BPM в диапазоне `[30, 300]`:
   `bpm = 60 · frame_rate / lag`.
3. Каждому кандидату присваивается оценка
   `score = acf[lag] · (1 + exp(−0.5 · (log2(bpm) − log2(start_bpm))²))` —
   ACF, умноженная на лог-нормальный приор с центром в `start_bpm` и шириной
   в одну октаву. Приор только усиливает (множитель в `[1, 2]`), не обнуляет.
4. **Выбор метрического кратного.** `select_preferred_tempo_candidate` берёт
   кандидата с максимальной оценкой; если он «подозрительно медленный»,
   ищется поддержанное кратное:
   - лучший < 75 BPM → ищем кандидата в `[115, 150]` BPM с отношением
     `1.80..2.20` (удвоение) и оценкой не ниже 50 % от лучшей;
   - лучший < 90 BPM → кандидат в `[120, 145]` с отношением `1.42..1.62`
     («полуторное», пунктирное кратное) и оценкой ≥ 75 %;
   - лучший < 95 BPM **и** его оценка ≥ 4.0 → то же окно и отношение, но
     порог 85 %.
   Среди подходящих берётся сильнейший. Иначе остаётся исходный лучший. Это
   эвристика под электронную музыку, где половинный пик ACF часто сильнее.
5. **Параболическая интерполяция.** `refine_tempo_from_acf_peak` уточняет
   лаг по трём точкам `acf[lag−1..lag+1]`: смещение
   `δ = 0.5 · (l − r) / (l − 2c + r)`, ограниченное `[−0.5, 0.5]`, и
   `bpm = 60 · frame_rate / (lag + δ)`. Это снимает квантование в 1–3 BPM от
   целочисленного лага. Если центр не является локальным максимумом или
   знаменатель вырожден — берётся целый лаг.
6. `tempo_raw` — уточнённый темп, зажатый в `[30, 320]`.
7. **Октавное сворачивание.** Если заданы **оба** `bpm_min` и `bpm_max`, темп
   удваивается, пока меньше `bpm_min`, и делится пополам, пока больше
   `bpm_max`. Требования: оба конечные, `0 < bpm_min < bpm_max`,
   `bpm_max ≥ 2 · bpm_min` (иначе сворачивание может зациклиться в дыре).
   Задан только один предел или диапазон уже октавы — ошибка
   `InvalidParameter("bpm_range")`. Результат снова зажимается в `[30, 320]`.
8. `candidates` — до 5 сильнейших пар `(bpm, score)` по убыванию оценки. Это
   **сырые** кандидаты ACF до выбора кратного и сворачивания; в результате
   конвейера они лежат в `bpm_candidates`.

Обратите внимание: поиск ведётся в `[30, 300]`, а зажим — в `[30, 320]`; разница
существует только для уточнённого или свёрнутого значения.

### Трекинг битов (DP)

1. Огибающая нормируется по z-score (`(v − mean) / (std + 1e−10)`).
2. `frames_per_beat = round(60 · frame_rate / tempo)`; если 0 — битов нет.
3. **Локальная оценка** — свёртка с гауссовым окном полушириной
   `frames_per_beat`, где `lag` масштабируется как `lag · 32 / fpb`, а веса
   `exp(−0.5 · lag²)`; сумма делится на сумму окна.
4. **Прямой проход.** Для каждого кадра `i` ищется лучший предшественник `j`
   в окне `[i − 2·fpb, i − fpb/2)` с наказанием за отклонение интервала:
   `cumscore[i] = local[i] + max_j (cumscore[j] − tightness · (ln(i−j) − ln(fpb))²)`.
   Порога нет: каждый кадр получает обратную ссылку (или ссылку на себя, если
   предшественника нет).
5. **Последний бит** — кадр с максимальным `cumscore` в хвосте длиной `2·fpb`;
   дальше обратный проход по ссылкам.
6. `trim` отрезает биты по краям, чья локальная оценка ниже 1 % от максимума.

Результат — кадры битов в той же системе индексов, что огибающая, то есть
конвертируются в секунды через `hop_length / sr`.

### `bpm_confidence` (конвейер)

Это **сигнал доверия, не вероятность**. В `analyze.rs`:

- `strength = s1 / (s1 + 1.2)`, где `s1` — оценка первого кандидата ACF;
- `agree = exp(−d / 0.10)`, где `d = |log2(bpm / bpm_beats)|`, свёрнутое на
  одну октаву (`min(d, |d − 1|)`), а `bpm_beats = 60 · n_beats / duration` —
  темп, каким его «видит» трекер по числу битов;
- `density = clamp(onset_density / 4, 0, 1)`;
- `bpm_confidence = clamp(0.50·strength + 0.35·agree + 0.15·density, 0, 1)`.

### `plp`, `tempo_curve`, `tempo_variability`

- `plp` (только Rust): по документации «Predominant Local Pulse через
  Фурье-темпограмму», но реализация проще: одна автокорреляция огибающей с
  максимальным лагом `min(384, n)`, поиск максимума в диапазоне
  `[tempo_min, tempo_max]` и импульсы `1.0` через каждый найденный период,
  начиная с кадра 0. Фазы к реальным битам нет. Считайте это заглушкой
  постоянного пульса, а не PLP из Grosche & Müller.
- `tempo_curve(beats, sr, hop, smooth)` — BPM каждого межбитового интервала
  (`60 / Δt`), длина `n_beats − 1`; `smooth = Some(k)` при `k ≥ 3` применяет
  медианный фильтр ширины `k` к внутренним точкам. Конвейер (фича `tempo_curve`,
   режим full или явный запрос) использует `k = 5`.
- `tempo_variability` — коэффициент вариации кривой (`std / mean`); 0 для пустой
  кривой. По комментарию в коде: < 0,05 — стабильный темп, > 0,1 — заметные
  колебания. Это оценка дрейфа, а не регулярности рисунка.

## Темпограммы и размер такта (`feature/rhythm.rs`)

### Автокорреляционная темпограмма

`tempogram(y | onset_envelope, sr, hop, win_length)`: огибающая нарезается на
кадры длиной `win_length` с шагом 1, каждый умножается на Hann и
автокоррелируется; столбец нормируется на свой максимум. Форма
`(win_length, n_frames)` — лаг × время. Если огибающая короче окна —
`InsufficientData`.

### Фурье-темпограмма

Те же кадры, но вместо ACF — `rfft` с окном Hann; результат комплексный,
`(win_length/2 + 1, n_frames)`. Частоты бинов в BPM даёт
`fourier_tempo_frequencies`.

### `tempo` (отдельная оценка темпа)

Отличается от трекера в `beat.rs`: строит ACF-темпограмму с окном
`min(384, n)`, усредняет по времени и берёт лаг с максимальной оценкой
`avg[lag] · (1 + exp(−0.5·(log2(bpm) − log2(start_bpm))²))` в диапазоне
`[30, max_tempo]` (по умолчанию 320). Ни выбора кратного, ни интерполяции здесь
нет, поэтому значения могут отличаться от `bpm` конвейера.

### `tempogram_ratio`

Для каждого кадра находит пиковый лаг и возвращает отношения энергии на
`1×`, `2×`, `3×` этого лага к пику — три строки. Единицы относительные.

### Метрограмма и размер такта

`metrogram` — оценка метра во времени по субгармоникам Фурье-темпограммы.
Для каждого отношения из `DEFAULT_METER_RATIOS` (`1/2, 1/3, 1/4, 1/5, 1/6, 1/7`,
соответствующие 2, 3, 4, 5, 6, 7 долям в такте) и каждого кадра:

`score[r, t] = Σ_b |F[b, t]| · |F|(freq[b] · ratio_r, t)`,

где второй множитель — линейная интерполяция модуля темпограммы на
субгармонической частоте. Столбцы нормируются на свой максимум, так что
значения относительные в `[0, 1]`.

`detect_time_signature(metrogram)` усредняет строки по времени, выбирает
максимум и возвращает `(label, confidence)`:

- `label` — всегда вида `"N/4"`, где `N` — числитель; для отношения `1/6`
  выдаётся `"6/4"`, отдельного `6/8` нет;
- `confidence = clamp((best − second) / best, 0, 1)` — **отступ от второго
  кандидата**, не вероятность. Пустая метрограмма → `("4/4", 0.0)`.

В конвейере это фича `time_signature` (full или явный запрос): окно `min(384, n)` кадров,
при окне < 4 результат `None`. Числитель дальше используется как
`beats_per_bar` для сетки и регулярности (если ≥ 2), иначе 4.

## Сетка битов (`beatgrid.rs`)

Фича `beatgrid` (opt-in). Работает на уже найденных битах и огибающей, стоит
`O(n_beats)` и не пересчитывает темп.

- **`grid_offset_sec`** — время первого бита: `beats[0] · hop / sr`; `0.0`
  без битов.
- **`downbeats`** — сильные доли. Для метра `bpb` перебираются `bpb` фаз:
  фаза `p` объявляет сильными биты `p, p+bpb, p+2·bpb, …`. Для каждой фазы
  считается **средняя** акцентная энергия — максимум огибающей в окне ±2 кадра
  вокруг бита (`ACCENT_WINDOW = 2`, потому что DP-трекер может стоять на
  кадр-два от пика). Побеждает фаза с наибольшим средним; при равенстве
  (плоская огибающая) — фаза 0. При `bpb = 1` все биты сильные.
- **`grid_stability`** — насколько биты ложатся на решётку постоянного темпа:
  `ibi_i` — межбитовые интервалы в кадрах, `m = median(ibi)`,
  `MAD = median(|ibi_i − m|)`, `stability = clamp(1 − MAD / m, 0, 1)`.
  Медиана и MAD выбраны, чтобы один пропущенный или удвоенный бит не
  доминировал. Меньше 3 битов → `0.0`.

Стабильность сетки описывает разброс межбитовых интервалов, включая дрейф,
джиттер и ошибки трекинга. При фиксированной сетке изменение синкоп внутри
такта не меняет эту метрику; для самого рисунка есть следующий модуль.

## Ритмическая регулярность (`rhythmic_regularity.rs`)

Фича `rhythmic_regularity` (opt-in). Отвечает на ортогональный вопрос: сетка
дана, где внутри неё лежат ударные события? Высокие значения — прямой рисунок
с акцентами на решётке пульса (house, techno); низкие — акценты на слабых
позициях, пропущенные сильные доли, пульсы, конкурирующие с метром (garage,
2-step, breakbeat, drum & bass). Модуль **не различает** нерегулярные идиомы
между собой и не является жанровым классификатором: это детерминированный
DSP-измеритель без модели, обучающих данных и встроенных артефактов.

Входы (в конвейере берутся из уже посчитанного): многополосные огибающие
`onset_bands` (нижняя полоса первой), биты, сильные доли из `beatgrid`, `beats_per_bar`,
`bpm_confidence`, `grid_stability` (при отсутствии считается на лету) и
необязательный `time_signature_confidence`.
Конвейер вычисляет beatgrid как внутреннюю зависимость даже без отдельного
запроса этой группы. Только при прямом Rust-вызове без downbeats фаза берётся
от первого бита. Внутренние поля сетки не попадают в результат без запроса.

### Алгоритм

1. **Татум-сетка.** Каждый межбитовый интервал делится на
   `TATUMS_PER_BEAT = 4` ячейки линейной интерполяцией между **реальными**
   битами, то есть 16 позиций на такт в 4/4. Геометрия задаётся относительно
   долей и следует за дрейфом темпа; численная оценка всё же зависит от
   разрешения исходной огибающей и качества трекинга. Ячейки **центрированы** на
   своей метрической позиции (`centre ± span / 8`), а не начинаются с неё:
   ранняя атака иначе уходила бы в предыдущий слот.
2. **Акценты.** Для каждой полосы в каждой ячейке берётся максимум огибающей по
   кадрам ячейки; ячейка всегда занимает минимум один кадр.
3. **Окна.** Такты группируются в непересекающиеся окна по
   `WINDOW_BARS = 4` такта; окно из одного такта пропускается (для оценки
   надёжности нужно ≥ 2 тактов).
4. **Циклический профиль.** В окне слоты складываются по модулю такта с фазой
   от сильных долей и усредняются по тактам: `P[j]`, `j ∈ 0..16`.
5. **Снятие DC.** `P̃[j] = P[j] − min_j P[j]`. Масса `Σ P̃` — вес полосы как
   свидетельства; плоская полоса (ровные шестнадцатые хэты, отсутствие ударных)
   весит ноль без ручных коэффициентов.
6. **Ворота надёжности** (`window_reliability`). Дисперсия профиля между
   слотами раскладывается на структуру и шум усреднения конечного числа
   тактов: `noise = mean_j Var_bars(A[bar][j]) / n_bars`,
   `signal = Var_j(P) − noise`, `reliability = signal / (signal + noise)`.
   Окно измеряется только при `reliability > 0.5` (структура объясняет больше,
   чем шум) — это следствие разложения, а не подобранный порог.
7. **Две ограниченные меры** на полосу, объединённые по полосам с весом массы
   и сложенные с равным весом:
   - **метрическое выравнивание** (`band_metrical_alignment`) —
     `⟨P̂, w⟩`, скалярное произведение L1-нормированного профиля с
     метрическими весами Лонге-Хиггинса и Ли. Веса: число уровней иерархии,
     которые слот начинает (для 4/4 и шестнадцатых — шаги `[16, 8, 4, 2, 1]`),
     аффинно отображённое так, что слабейший слот 0, сильная доля 1. Результат
     читается между двумя опорами: `uniform = mean(w)` (метрически слепая
     масса → 0) и `lattice` = среднее `w` по слотам долей (ровные четыре удара
     → 1), с зажимом. Фазочувствительна: ловит кик, смещённый на слабую
     шестнадцатую.
   - **суб-тактовая периодичность** (`band_metrical_periodicity`) — доля
     AC-энергии (бин 0 исключён) 16-точечного DFT профиля на бинах, кратных
     `L / sub_bar_period`, где `sub_bar_period` — первый уровень ниже такта
     (полутакт = 8 слотов в 4/4). Это в точности доля фигуры, повторяющейся
     **внутри** такта. Нуль-опора — `(p − 1) / (L − 1)` (доля таких бинов по
     счёту). Мера фазонезависимая, её дополнение — `pulse_competition`,
     энергия пульсов, конкурирующих с метром (три-на-четыре и т. п.).

   `regularity_window = 0.5 · (alignment + periodicity)`.

   Ещё две меры считаются и **отдаются как диагностика, но в счёт не входят**:
   `beat_concentration` (масса на четвертях против массы между ними, с
   нуль-опорой `1/4`) и `beat_coverage` (перплексия `exp(H)` распределения массы
   по долям, нормированная между одной долей и всеми). Причины исключения в
   коде и корневом README: оба спрашивают «кик на четвертях?», а 93-мс окно
   STFT не разрешает, **какую** шестнадцатую занимает низкочастотная атака, и
   broken-beat house смещает кик **внутри** доли, что эти меры не видят.
8. **Робастная агрегация.** Значение трека — взвешенная медиана по валидным
   окнам с весом `mass · reliability`; это уменьшает влияние отдельных
   брейкдаунов и сбивок, пока они не набрали существенный вес.

### Что возвращается

| Поле | Смысл |
| --- | --- |
| `regularity` | `[0, 1]`, `None` при воздержании |
| `label` | `"regular"` при `≥ 0.5`, иначе `"irregular"`; граница — середина шкалы, не подобранная |
| `candidates` | `[(label, score)]` по убыванию; оценки взаимодополняющие (`r` и `1 − r`), это измерения, не вероятности |
| `confidence` | качество свидетельств, всегда присутствует |
| `beat_concentration`, `beat_coverage`, `metrical_alignment`, `metrical_periodicity`, `pulse_competition` | диагностические компоненты (медианы по окнам) |
| `pattern_stability` | средняя косинусная близость профилей окон к консенсусу; 0 при одном окне |
| `windows_total`, `windows_valid` | сколько окон дала сетка и сколько прошли ворота |
| `beats_per_bar` | метр, по которому складывался профиль |

В результате `analyze_*` наружу выходят четыре поля: `rhythmic_regularity`,
`rhythmic_regularity_label`, `rhythmic_regularity_confidence`,
`rhythmic_regularity_candidates`; диагностические компоненты доступны только
через Rust-структуру.

### Воздержание

Мера **воздерживается, а не гадает**. `regularity`, `label` и `candidates`
становятся `None` одновременно, если:

- нет полос, нет кадров или меньше 2 битов;
- фаза сильной доли не оставляет ни одного полного такта;
- ни одно окно не прошло ворота надёжности (тишина, эмбиент, безударный
  фрагмент, ровный постоянный поток — «чистый DC»).

`confidence` при этом всё равно отдаётся (обычно `0.0`), поэтому вызывающий
код отличает «нерегулярно» от «не смог определить». `None` означает
«измерено, свидетельств нет», а не «не считалось».

### `confidence` — качество свидетельств, не вероятность

Геометрическое среднее факторов (любой нулевой фактор обнуляет всё, потому что
свидетельства конъюнктивны):

- `bpm_confidence` — татум-сетка строится от битов;
- `grid_stability` — образуют ли биты решётку вообще;
- `1 − 1/√n_valid` — стандартная ошибка агрегации по окнам; одно окно даёт 0;
- средняя надёжность окон;
- `pattern_stability` — повторяемость рисунка между окнами. Он входит **только
  в доверие**, никогда в счёт: стабильный брейкбит остаётся брейкбитом;
- `time_signature_confidence`, если размер такта тоже запрашивался.

### Ограничения, зафиксированные в коде

- Фаза наследуется от трекера: если тот зацепился за офбитные хэты (редкий
  кик, разреженная фактура), фазочувствительные компоненты проседают; счёт
  деградирует, а не переворачивается, потому что периодичность фазонезависима.
  Индикатор — `bpm_confidence`.
- Шестнадцатая на краю разрешающей способности: окно STFT 2048 отсчётов —
  93 мс против 117 мс шестнадцатой при 128 BPM, флюкс «утекает» в соседнюю
  ячейку. Сетка восьмых убирает утечку, но измеряет меньше и по коду
  показала худшее разделение классов, поэтому оставлены шестнадцатые.
- Это дескриптор ритма, не жанра: house-трек с брейкбит-секцией прочитается
  так, как звучит его ритм.

Числа AUC, точности и размеры выборок в docstring модуля и в корневом README
(130 против 145 размеченных треков в разных местах) — исторические результаты
локальных корпусов на момент 0.3.7, а не проверяемые из репозитория факты.
Свежая отложенная контрольная выборка для «прямой» стороны, по README, отсутствует.

## Тональный слой (`tonal.rs`)

### Спектральные пики

`detect_spectral_peaks` работает на **амплитуде** (`sqrt` мощности): локальный
максимум по трём бинам, порог `threshold` (по умолчанию 0), диапазон частот
`[min_freq, max_freq]` (по умолчанию 40–5000 Гц), параболическая интерполяция
частоты и амплитуды по трём точкам, сортировка по убыванию амплитуды, обрезка
до `max_peaks` (50). Один и тот же набор пиков питает и HPCP, и диссонанс —
как в `hpcp_and_dissonance`, так и в fused-цикле `analyze.rs`, где та же логика
продублирована инлайн с константами `MAX_PEAKS = 50`, `N_HPCP_HARMONICS = 4`.

### HPCP

Harmonic Pitch Class Profile по Гомес (2006). Для каждого пика и каждой из
`n_harmonics` гармоник `h = 1..4` (веса `1/h`):

1. `f = f_peak / h`; частоты ниже 20 Гц пропускаются;
2. непрерывный класс высоты `pc = (12 · log2(f / C_REF)) mod 12`, где
   `C_REF = 261.6256` Гц (C4 при A4 = 440);
3. вклад идёт в **ближайший** класс с косинусным весом
   `w = cos(π · dist)` при `dist < 0.5` полутона, иначе 0;
4. накапливается `weight_h · mag² · w`.

Строка кадра L1-нормируется (сумма 12 классов = 1; нулевой кадр остаётся
нулевым). В fused-пути нормировка делается отложенно, только когда запрошены
`chords` или `dissonance`. Форма `(12, n_frames)`. HPCP — это отдельная
величина от «хромы» конвейера (`chroma_mean`), которая считается разреженным
хрома-фильтром по мощности и нормируется по L∞ на кадр.

### Аккорды

Шаблоны — 24 триады: мажор `{0, 4, 7}` и минор `{0, 3, 7}` для всех 12 тоник.
`match_chord` берёт косинусную близость (нормированное скалярное произведение)
между усреднённым HPCP сегмента и каждым шаблоном; побеждает максимум. Нулевой
HPCP даёт `("maj", C, 0.0)`. Метки: `"C"`, `"C#"`, …, минор с суффиксом `m`
(`"Am"`). Септаккорды, уменьшённые и увеличенные трезвучия не распознаются:
любой звук отображается на ближайшую мажорную или минорную триаду.

- `chords_from_beats(hpcp, beats)` — границы сегментов
  `[0?] + beats + [n_frames?]` (`chord_boundaries`), HPCP усредняется внутри
  каждого; пустой сегмент помечается `"N"`. Число меток = число границ − 1.
- `chords_from_frames(hpcp, segment_frames)` — сегменты фиксированной длины.
  Docstring говорит «по умолчанию ~0,5 с», но Python-обёртка использует
  `segment_frames = 10` (≈ 0,23 с при 22050/512).
- `chord_descriptors(chords, duration_sec)` — `predominant_chord` (самый частый;
  при равенстве — лексикографически меньшая метка, чтобы результат не зависел
  от порядка), `change_rate` = число смен соседних меток / секунды,
  `n_unique`. Пустая последовательность → `("N", 0.0, 0)`.

В конвейере (фича `chords`, extended) аккорды идут по битам; дополнительно
строятся `chord_events` — слитые подряд одинаковые метки с `start_sec`/`end_sec`
(последнее событие закрывается длительностью трека).

### Диссонанс

Модель Сетареса (1998), параметризация кривой Пломпа–Левельта:
`b1 = 3.5144`, `b2 = 5.7564`, `d_max = 0.24`, `s1 = 0.0207`, `s2 = 18.96`.
Для каждой пары пиков `s = d_max / (s1 · f_min + s2)`,
`d = max(exp(−b1·s·Δf) − exp(−b2·s·Δf), 0)`, вес `m_i · m_j`. Значение кадра —
взвешенное среднее `d` по парам, зажатое в `[0, 1]`; меньше двух пиков → 0.
Трек — среднее по **всем** кадрам, включая те, где пиков не хватило (они дают
0). Октава близка к 0, малая секунда заметно выше. Это сенсорная шероховатость
спектра, не музыкально-теоретическая оценка гармонии.

## Тональность (ключ) в `perceptual.rs`

`detect_key(chroma)` принимает 12-мерный вектор (в конвейере — `chroma_mean`,
среднее L∞-нормированных хром по кадрам). Несмотря на слово
«Крумхансл–Шмуклер» в docstring, профили — **Темперли** (MIREX 2005),
корпусные, лучше подходящие для популярной музыки. Для каждого из 12 сдвигов
считается корреляция Пирсона хромы с мажорным и минорным профилем (24
гипотезы); побеждает максимум, при равенстве — первая встреченная.

- `key` — тоника из `C, C#, …, B` (только диезы); `mode` — `"major"` /
  `"minor"`; `format_key` даёт строку вида `"A minor"`.
- `confidence = clamp((best − second) / |best|, 0, 1)` — **отступ от второго
  лучшего профиля**, не вероятность и не корреляция сама по себе. Вектор не
  длины 12 → `C major` с доверием 0.
- `detect_key_candidates` (фича `key_candidates`, opt-in) повторяет те же 24
  корреляции и отдаёт топ-3 как `(строка ключа, код Camelot, score)`, где
  `score` — сама корреляция Пирсона, зажатая в `[0, 1]`. Первый кандидат
  гарантированно совпадает с `detect_key` (стабильная сортировка, мажор перед
  минором при каждом сдвиге). Шкалы `score` и `key_confidence` разные: первая —
  сила соответствия, вторая — отрыв.
- `camelot(tonic, mode)` — код колеса Camelot: минор в кольце «A» (A minor →
  `8A`), мажор в «B» (C major → `8B`); принимает диезные и бемольные написания
  и краткие `maj`/`min`; неизвестный вход → `None` (`key_camelot` вместо этого
  возвращает `"?"`).

В конвейере ключ выдаётся при запросе `key` или `valence` (последней он нужен
как вход); если ключ считался только ради `mood`, поля `key`, `key_confidence`,
`key_camelot` остаются `None`.

## Что измерение, а что нет

| Величина | Природа |
| --- | --- |
| `bpm`, `bpm_raw`, `beats`, `tempo_curve` | измерение (BPM, кадры) |
| `bpm_candidates[*].score`, `key_candidates[*].score` | сырые оценки (взвешенная ACF; корреляция Пирсона) |
| `bpm_confidence`, `key_confidence`, `time_signature_confidence`, `rhythmic_regularity_confidence` | сигналы доверия/отрыва в `[0, 1]`, не вероятности |
| `grid_stability` | дрейф сетки, `1 − MAD/median` |
| `rhythmic_regularity` | положение акцентов внутри сетки; `candidates` — `r` и `1 − r`, не распределение |
| `chord_sequence`, `key` | категориальные метки по шаблонам (24 триады; 24 профиля) |
| `dissonance` | сенсорная шероховатость по Сетаресу, `[0, 1]` |

## Ограничения, общие для слоя

- Всё построено на одной огибающей спектрального потока при `hop = 512` и
  `n_fft = 2048`: временное разрешение ≈ 23 мс, окно 93 мс. Быстрые
  субдивизии и очень высокий темп упираются в это.
- Диапазон темпа `[30, 320]` BPM и приор на 120 BPM: медленная или очень
  быстрая музыка чаще получает октавную ошибку; `bpm_min`/`bpm_max` —
  единственный штатный способ задать желаемую октаву, и он требует диапазона
  не уже октавы.
- Метр определяется только как `N/4` при `N ∈ {2..7}`; сложные и составные
  размеры сводятся к ближайшему числителю.
- Тональность и аккорды — бинарные мажор/минор по 12-классовой хроме; модальные
  и атональные фрагменты получат ближайший шаблон с низким доверием.
- Тесты регулярности проверяют повторяемость на фиксированном входе.
  Это не гарантия битового совпадения всех DSP-функций между платформами,
  версиями компилятора и численными backend.

## Расхождения документации и кода, найденные при написании

- `beat.rs::plp` документирован как PLP через Фурье-темпограмму, но реализует
  одну ACF и импульсы с нулевой фазы.
- `perceptual.rs::detect_key` назван алгоритмом Крумхансла–Шмуклера, профили
  при этом Темперли.
- `tonal.rs::chords_from_frames` обещает сегмент «~0,5 с» по умолчанию;
  Python-значение по умолчанию `segment_frames=10` ≈ 0,23 с при 22050/512.
- Оценка темпа ищет кандидатов в `[30, 300]` BPM, а зажимает в `[30, 320]`.
- Размер выборки для регулярности в docstring (`130` треков, 30 broken) и в
  README (`145`, 45 broken) различается; обе цифры — история, не контракт.
